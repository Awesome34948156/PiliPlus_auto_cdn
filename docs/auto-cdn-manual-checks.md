## 0. 先把日志打开（所有检查都依赖它）

设置 → 视频设置页（入口副标题「画质、音质、解码、缓冲、音频输出等」，
`lib/pages/setting/models/video_settings.dart`）。打开：

- **「卡顿自动切换 CDN」** → `SettingBoxKey.autoSwitchCdnOnStall`（默认开）。
  **必须开**：关掉时 `_cdnAutoEligible` 为假，每条检查都会卡在资格门上。
- **「详细播放日志」** → `SettingBoxKey.mpvVerboseLog` → `Pref.mpvVerboseLog`
  （`lib/utils/storage_pref.dart:517`）。它把 mpv 的 `logLevel` 抬到 `.v`，但
  **只在控制台出口开着时生效**：`lib/plugin/pl_player/controller.dart` 的 `_initPlayer()`
  `logLevel: consoleLogActive && Pref.mpvVerboseLog ? .v : (kDebugMode ? .warn : .error)`。
- **「CDN 切换提示」** → `SettingBoxKey.showCdnSwitchToast`（默认开）。可选，
  给同一批事件做旁证。

**控制台日志开关不是一个用户设置**，别去找：捕获钩子在启动时无条件装上
（`installConsoleLogCapture()`，`lib/main.dart:100`），开关是 getter
`consoleLogActive`（`lib/services/console_log.dart:101`，`=> _sink != null`）——
正常手机包上文件能开就是 true，所以只开「详细播放日志」就够了。

日志文件：应用文档目录下的 **`pili-console.log`**（`_kConsoleLogName`，
`lib/services/console_log.dart:28`）。用 adb / 文件 App / iOS 文件共享取回，或直接
看控制台。iOS 上 `UIFileSharingEnabled` + `LSSupportsOpeningDocumentsInPlace` 都开着，
所以「文件」App → 我的 iPhone → PiliPlus 里直接就有这个文件。

**iOS 上更省事的一条路（2026-10-12 加，**同日真机已验证 ✅**）：iCloud 日志同步。**
设置 →「其它设置」
（`SettingType.extraSetting`）里的一行「iCloud 日志同步」→ 选择 iCloud Drive 里的
一个文件夹，之后 app **每 60 秒**把日志同步一份过去，**退到后台立刻再同步
一次**。Mac 上直接读：

```
ls ~/Library/Mobile\ Documents/com~apple~CloudDocs/Downloads/ForpiliLog/
```

**验收证据**：2026-10-12 20:32 那一份与同时用 `devicectl` 拉下来的 1500 行
**逐字节相同、只少最后一行**（那一行是快照之后才写进本地日志的）——
少的那一行本身就是"这是活体快照"的证明。
⚠️ **成功时它一行日志都不打**：日志里 grep 不到任何 iCloud 字样 **≠** 没生效。
上一版踩的坑记在这儿：`bookmarkData` 必须**在** `startAccessingSecurityScopedResource()`
**之后**调，反过来抛 `The file couldn't be opened because it doesn't exist.`
（`ios/Runner/ICloudLogPlugin.swift:136-170`）。

人不在电脑边上、手机不在同一个 Wi-Fi 上（`devicectl` 拿不到）时这条是唯一的路。
每次启动会把上一份改名成 `pili-console-<MMdd-HHmmss>.log`，只留最近 10 份。
⚠️ 挑文件夹时请挑 **iCloud Drive** 里的，挑成「我的 iPhone」就永远同步不到 Mac ——
这一点 app 拦不住。⚠️ Mac 上晚几分钟才看到不代表没写：上传是系统的 `bird` 在跑，
低电量模式、关了蜂窝的 iCloud Drive 都会拖后。**以设置页副标题里那个「上次同步
时刻」为准。** 书签失效（文件夹被改名/移走）时 app 会自动退回「未设置」并提示重选，
不会崩也不会刷屏。

**每条物理行都以 `HH:mm:ss.SSS ` 开头**（`_stamp`，2026-10-11 加）。下面表格里那些
"逐字发出的行"指的是戳**之后**的那一段 —— grep 子串照样命中。加戳的理由：换源的一半

⚠️ **每次启动都会把这个文件截断重写**（`writeAsString('')`）。测完**别杀进程、别重启

> **解码档的回执（P1 的另一半，2026-10-13 修）**：`onDecodeError` 这条通道现在**有回执**
> （播放器侧类型 `bool Function(Duration)`）。页面在**在途轮次**（busy）里收不下解码风暴时

>   应在**轮次收尾后**补上 —— 随后的日志里能看到 `CDN 看门狗: 解码错误风暴…` →
>   `解码错误 @Ns，当前镜像给的是坏字节…`。
>   （配一个坏源 + 一个还在途的轮次才撞得到；机理与取证见 memory `cdn-freeze-corrupt-mirror`。）
> - **反证**：**非解码**触发（如 `卡顿`）在 busy 里**仍然**被挡下、**不重报** —— 回执只改了
>   `decode` 这一条通道；`diverged` / `starve` 维持各自的 20s 补报，**别顺手统一**。
> - **不新增日志字符串**：重报打的仍是原有那两行，**速查表一条都不用加**。

### 1 — 回拖会永久关掉闸门（HIGH）

前置：必须有一轮**"切了但没成功"**的账。`_cdnState.lastAttemptPos` 只在**切换那一刻**
置非零（`cdn_switch_mixin.dart` 的 `_cdnState.lastAttemptPos = stalledAt`），而一轮
**成功**会把它归零（同文件的 `成功，已切到` 那一行）—— 所以光看到 `第1次 ->`
**不算数**，必须看到那一轮最终是 `… 未恢复，换下一个候选` → … → `放弃`。

> 实测（2026-10-11）：那一轮是 `第1次 -> tf_hw` → `未恢复` → `第2次 -> hw` →
> `成功，已切到 hw`，闸门**当场归零**。此后回拖无论怎么拖都不会有任何一行 ——
> 不是漏了，是闸门根本没关上过。

步骤：等上面那种"切了又放弃"的一轮结束，**过掉那 60s 放弃冷却**（否则只会看到
`冷却中，忽略…`），然后往回拖 ≥3s，再立刻制造一次卡顿/饥饿。

通过：出现**新的**触发行（如 `CDN 自动切换: 卡顿 @Ns，开始找可用镜像`），且里面的
位置是**变小后**的新位置 —— 它同时证明了回拖那一支确实把非零值清掉了。

失败：**拖完之后再等多久都没有新的触发行**（不是"出现 `Δ 为负` 的行"，见下）。

⚠️ `CDN 自动切换: 距上次尝试只推进了 -Ns，忽略` 里 **Δ 为负是打不出来的**：
代码先做 `if (position < _cdnState.lastAttemptPos) _cdnState.lastAttemptPos = Duration.zero`，
紧接着的闸门又要求它非零 —— 两条合起来 Δ 只可能 ≥0，那行只在"位置只推进了 0~2 秒"
时出现。拿它当本条的失败证据是清单早期版本的笔误（2026-10-11 修正）。

`playRepeat` 循环播放也会这样复现。

### 2 — 换画质 = 新的对象：重新探大小、不出现 416 循环、不毒化死镜像冷却（MEDIUM）

前置：1080P 在播，`_cdnState.objectSize` 是大对象长度。记住 `目标偏移 …/<大size> 字节`。
步骤：切画质 1080P→360P（`updatePlayer` → `resetCdnForNewObject`），然后制造卡顿。
通过：下一轮打印的 `目标偏移 <off>/<新size> 字节` 用的是**新**size；候选行照常出现
（`… | [<svc>] <r>MB/s …` 或 `无样本`），**不出现**
`CDN 自动切换: 目标偏移 <off> 越界(416)，放弃本轮`；候选池也不空
（不出现 `没有可测的候选镜像`）。416 那条 return 在 `_cdnState.noSample` 记账**之前**，
所以没有镜像被锁 30 分钟。
失败：整集每轮都以 `越界(416)，放弃本轮` 收尾，随后 `没有可测的候选镜像`
（死镜像冷却 `CdnTuning.deadRetryAfter` = 30 分钟被毒化了）。

### 3 — 作废的那一轮不许清忙闸（MEDIUM）

前置：制造一个能拖住的换源（限速下的慢卡顿），使 `_cdnState.autoBusy == true` 并已出现 `第1次 ->`。
步骤：那一轮还在跑时换画质（`resetCdnForNewObject` → `_cdnState.generation++`），再触发一次卡顿。
通过：后一次触发被**认了** —— 打印触发行 + `第N次 ->`，且永远不出现
`(busy=true …)` 的 `忽略…` 行。代际不匹配让旧轮的 `whenComplete` 跳过清忙，闸门归新一代。
失败（少了条目 3）：两轮并发，出现两组交错的 `第N次 ->`。
失败（少了条目 2）：此后每次触发都 `忽略<what> @Ns (busy=true …)`，永久卡死。

### 4 + 10 — 取样点落在**缓存末端之后**；时长未知时退回内部下界（MEDIUM/LOW）

前置：任意一集在播，盯着 `目标偏移 <off>/<size> 字节 (位置 <posMs>ms/<durMs>ms)`。
步骤：正常播（缓冲健康、bufferedAhead > 0），再让它饿到 0。
通过：`<off>` 对应 `(max(cacheEnd, playhead) + 5000ms) / durMs × size` —— 落在播放头
字节**之后**、也落在缓存末端之后，且 ≥ `size × 0.15`（15% 下界）、≤ `size − 4MiB`。
当 `<durMs>` 是 `0`（刚装载、时长还没到）时，偏移是**内部下界** `size × 0.15`，
不是 `0`（不是头部）。只有听视频（`onlyPlayAudio`）或 size 未知/为 0 才给 `0`。
失败：`目标偏移` 等于头部（`0`，或冷启动时的播放头字节）—— 头部每个镜像都快，
样本打平、比值 ≈ 1，即使尾段真的坏也报 `没有找到更快的镜像` / 永不切换。

### 5 — 关掉控制台日志时采样仍要活着（MEDIUM）

前置：release 或 debug 包都行；把日志关掉（「详细播放日志」OFF），能造出
`consoleLogActive == false` 更好。喂坏字节（坏镜像/代理吐垃圾，或实测那个 AV1 1080P 场景）。
步骤：让坏源播上几秒，攒够一轮报错。
通过：`CDN 看门狗: 解码错误风暴（6s 内 12 条），当前镜像给的字节解不出画面 —— 上报换源`
照样出现，后面跟一个 `解码错误 @Ns…` 触发。`stream.log` 订阅现在是无条件的，
`_sampleDecodeError(log.text)` 对每条消息都跑，跟 `kDebugMode`/`consoleLogActive` 无关。
失败：报错在刷（mpv 那边照写），但看门狗那行永不出现 —— 判据静默失明，正是修复前的行为。

### 6 — 账在换集/换画质时归零，但**换源时不归零**（MEDIUM）

前置：坏源，默认档位（logLevel `.error`）。
步骤 (a)：风暴中途换集（或换画质），新一集得从头攒。
步骤 (b)：同一集里，让一场风暴横跨一次自动换源（重载会排空旧流的报错）。
通过 (a)：换集后**不立刻**出现看门狗行 —— 必须重新攒满 12 条/6s；旧流的账不带过去
（页面 `onReset`（`controller.dart:1315`）调 `resetCdnAutoSwitch()`（`:1325`），由它在混入层把播放器的解码账清掉（`plPlayerController.resetDecodeErrorAccounting()`）；
换画质走 `resetCdnForNewObject()`，清理就在那个方法里）。
通过 (b)：换源期间旧流的报错**继续计数** —— 换源前会触发的那场风暴，换源后照样触发
（`_decodeErrors` 刻意不在 `player.open`/`setDataSource` 里清）。
失败 (a)：新一集的 host 被上一集残留的风暴瞬间禁掉。
失败 (b)：每次重载都把计数清零，风暴永远攒不满 12，换源永不发生。

### 7 — 解码档按干净窗口判恢复；换入的 host 会被禁；最终干净地放弃（HIGH）

前置：源级坏字节（所有镜像的字节一样坏 —— 比如坏上传，或代理对每个 host 都吐垃圾）。
默认档位即可。
步骤：播到解码风暴触发，让循环跑到头。
通过：每次尝试都由干净窗口裁定，只有在画面真的干净时才打印
`CDN 自动切换: 解码错误档换源后 Ns 无新报错，判定已恢复`（≥4s 宽限之后再有 ≥4s 安静，
**合计 ≥8s**；日志里那个 Ns 是"观察到的安静时长"，所以它在成功时应 ≥4）。
仍然坏的镜像被禁：`CDN 自动切换: <host> 换过去仍解不出画面，本集不再作为候选`；
换到好源以 `CDN 自动切换: 成功，已切到 <svc>` 结束。对全坏的源，收敛到
`第N次 -> …` 最多 `CdnTuning.maxAttempts`（3）次，然后放弃：
`CDN 自动切换: 放弃，Ns 内不再尝试（换了几处镜像，画面仍然解不出来，已暂停尝试）`。
失败：快但坏的镜像在 ~0.5s 内被判"已恢复"（走的是余量/位置那条），画面还冻着；
循环在同样几个 host 之间来回弹，而不是逐个禁掉再放弃。
注意强制档的总上限是 `CdnTuning.decodeRecoverWindow`（18s），不是 12s 的 `CdnTuning.recoverWindow`。

### 8 — 跳相关视频后，旧页面的探测定时器要静音（MEDIUM）

前置：播一个视频，看着探测节奏（起播后每 2s 一次预检，之后 `定期测速` 每 2 分钟）。
步骤：从播放页点一个**相关视频**（会 push 第二个 `/videoV`，不关第一个）。
让新视频起播；等过至少一个旧节奏窗口（≥2 分钟，且越过旧页面的下一次预检轮询）。
通过：旧页面的定时器在下一拍自我取消 —— `_cdnIsAttached`
（现在问的是播放器：`cdnSwitchCallbacksOwnedBy(_cdnClaimToken)`，即那组回调仍登记在本页
的 owner token 名下；**不再是**旧的 `onStall == _onPlayerStall` 同一性判断）
为假，`_onCdnProbeTick` 取消 `_cdnState.probeTimer` 后静默返回。此后**不再**出现
属于前一个视频的 `CDN 自动切换: 预检 @Ns…` / `定期测速 @Ns…`；只剩新页面的节奏。
失败：新视频在播之后，仍然冒出 `预检`/`定期测速`（或 `第N次 ->`）且播放器用**旧视频的 URL**
重载 —— 表现为新视频莫名回跳/重载。

> ✅ **已通过（真机，2026-10-11）**：播 A（对象 `543447102` 字节）→ 点相关视频进 B
> （B 的对象是 `94814278`）→ B 播一段再回 A。
>
> **正面那一半才是证据。** 回 A 之后 `22:13:36.188 CDN 自动切换: 预检 @37s` 出现，
> 后面的 `目标偏移 81517065/543447102 字节 (位置 37000ms/2225075ms)` 用的是 **A 的
> 对象、A 被盖住时的位置**。而 `attachCdnSwitch` 是幂等的
> （`if (_cdnIsAttached) return;`，见 `attachCdnSwitch()`），预检能重开
> **只可能**是因为重挂那一刻 `_cdnIsAttached` 为假 —— 也就是说 B 在播的那段时间里，
> A 确实已经不挂在播放器上了。重挂的因果也是闭合的：`restartCdnProbe()` 只有两个
> 调用点（`controller.dart:1327` 的 `onReset`，只有换 P/换集走得到；
> `attachCdnSwitch()` 里），返回 A 时唯一可能是后者，
> 而它在返回路径上的调用点只有 `view.dart:498`（`didPopNext`）。时间也对：
> 返回 `22:13:33.844` → 预检 `22:13:36.188`，2.34 s，正是 `CdnTuning.preflightPoll`
> 的 2 s 加上等缓冲那一拍。
>
> ⚠️ **负那一半（"旧页面静默"）不构成证据，别拿它当通过的依据。** 旧页面的周期
> tick 只有在 `bufferedAhead` 低于回填水位时才打印（`_onCdnProbeTick` 里
> `if (bufferedAhead >= floor) return;`），而那段
> 余量一直 22~31s，很健康 —— 所以"窗口里没有带 A 对象长度的行"这件事，
> **A 已静默**和**A 仍挂着但没到该响的时候**两种解释都成立。
> （清单早期版本写过"那 138 秒里一条 `CDN 自动切换:` 都没有"，**是错的**：
> 那一段 `22:11:15` → `22:11:22` 有 7 行，是 **B 自己的**预检，
> 对象是 B 的 `94814278`；2026-10-11 复核时改正。）
> 顺带一句：`CDN 看门狗: 余量 …` 那串心跳是**播放器单例**打的，不属于任何一页，
> 别把它当成"某页还在活动"的证据。

### 9 — 某个候选的 416 不该作废整轮（LOW）

前置：一轮里 1 个基线 + ≥2 个候选，其中一个候选的对象更短/不接受该 range（在该偏移回 416）。
步骤：制造卡顿，看这一轮。
通过：该候选在本轮汇总里就是 `无样本`，并产生 `CDN 测速失败 <label>: <DioException 416>`；
**其他**候选的样本保留、本轮继续。`offsetRejected` 只在 `isBaseline` 为真时置位。
若**基线**回 416，整轮正确作废：`目标偏移 <off> 越界(416)，放弃本轮`。
失败：单个候选的 416 就产生 `越界(416)，放弃本轮`，把好候选的样本一起丢掉，
还白搭 20s 的 `CdnTuning.unmeasuredCooldown`。

### 11 — 零字节镜像不该被重新排进候选（LOW）

前置：让一个镜像进入 `_cdnState.noSample`（某轮它一个字节没到 → `[<svc>] 无样本`）。
步骤：同一集里立刻再来一轮（再制造一次卡顿）。
通过：零字节镜像在放宽的第二遍里被跳过 —— 不出现在下一轮的样本行里；
只在第 1、2 遍都填不满窗口时才走第 3 遍「全都不管」。有可用候选时不该出现
`CDN 自动切换: 没有可测的候选镜像`。
失败：零字节镜像每轮都被重新排进去，每次白搭两个 3s 超时
（`CdnTuning.deadRetryAfter` = 30 分钟就是为了防这个）。

### 12 — 换集时 `_cdnState.quickProbeAt` 要归零（LOW）

前置：触发一次小卡顿探测，让 `_cdnState.quickProbeAt` 打上时间戳（出现 `小卡顿 @Ns…`）。
步骤：30s 内（`CdnTuning.rebufferCooldown`）换到下一集，再制造一次余量归零。
通过：新一集的小卡顿打印
`CDN 自动切换: 小卡顿 @Ns，余量刚归零，后台快速测一轮（快速档 NNNkB × 3，不看缓冲水位）`
—— 节流被 `resetCdnAutoSwitch` 清了（`_cdnState.quickProbeAt = null`）。
失败：打印的是 `CDN 自动切换: 小卡顿冷却中（距上次 Ns），只记不测 @Ns`，N < 30 且指的是
**上一集** —— 新一集开头 30s 的小卡顿全被压住。

### 13 — 暂停后强制换源：播放必须保持暂停（LOW）

前置：坏源；暂停播放（缓冲里残留的坏字节仍可能凑够一场风暴）。
步骤：暂停，等解码风暴触发（`CDN 看门狗: 解码错误风暴…` → `解码错误 @Ns…`）。
通过：换源照跑，但播放**保持暂停** —— `_switchTo` 现在读
`final wasPlaying = plPlayerController.playerStatus.isPlaying;` 再
`playerInit(autoplay: wasPlaying)`，位置不前进、暂停态保留；用户的
`Pref.autoPlayEnable` 偏好也不被改写。
失败：重载后自己播起来了（旧代码写死 `autoPlay = true`）。

### 14 — 强制档也不许落到喂不动的镜像上（LOW）

前置：坏源，且 `needBps` 已知（size 与 duration 都探到）；唯一候选很慢（~43 KB/s）。
步骤：让解码触发出手，候选被测完。
通过：`CDN 自动切换: 解码错误，但没有候选能满足 <needBps>MB/s 的码率，放弃本轮`
—— 因为 `needBps > 0 && bestBps < needBps`，宁可拒绝也不落到不可播的镜像上。
size/duration 未知（`needBps == 0`）时跳过这道守卫，行为与原来一致
（强制档绕过 `CdnTuning.starveRatio` 仍然成立）。
失败：循环换到那个 ~43 KB/s 的镜像上（`第N次 ->` 之后接着饿），而不是拒绝。

### 15 — 大小写不同的解码报错仍要认得（LOW）

前置：主要是**单测**（`test/utils/decode_error_test.dart` 覆盖
`av1: OBU_Forbidden_Bit Out Of Range`、`INVALID NAL UNIT SIZE`）。真机上只是抽查。
步骤：坏源下把 `pili-console.log` 里的原始 mpv 行捞出来，确认即使 ffmpeg 用混合/大写
发签名，仍然能产生看门狗行。
通过：`isDecoderCorruptionLog` 两边都转小写（`_kDecoderCorruptionSignaturesLower`），
比如 `metadata obu type` 任意大小写都能匹配、都能触发 `CDN 看门狗: 解码错误风暴…`。
失败：某个大小写变体（如 `Error Parsing OBU Data`）流过去了却没有看门狗行 —— 判据静默失效。

### 16 — 时钟回拨会让记录过期（LOW）—— **只能单测**

没有控制手机系统时钟就测不了。由 `test/utils/cdn_speed_test_test.dart` 对着桩时钟覆盖：
`CdnSpeedTest.recordTooOld(now, recorded, window)` 在 delta 为负（NTP 回拨/用户改时钟）
以及 `delta >= window` 时都返回真，所以一条峰值记录活不过 6 小时的作废线，
「重新开窗」那道守卫也照样触发。真机上唯一的症状是"一条陈旧峰值记录永不过期"，
手动触发不到。

### 17 — 风暴门槛数的是**包**不是日志行（LOW）

前置：坏源；一个坏包会被 ffmpeg 的各层（`av1:` / `libdav1d:` / `NULL:`）发 2~3 行。
步骤：真机上看 `CDN 看门狗: 解码错误风暴…` 是相对多少个**坏包**触发的；
去重窗是 `PlayerTuning.decodeLineDedupe = 5ms`（距上一条 5ms 内的算同一个包，不计入）。
通过：需要约 12 个**不同**的坏包（每个包 5ms 内的多层重复只算一条），而不是约 4 个。
要精确确认看纯函数单测 `recordDecodeErrorHit`（`test/utils/decode_error_test.dart`）。
失败：只攒到约 4 个坏包就触发（修复前的有效门槛），即三层的重复被各记了一条。

**后面又加了一档**（2026-10-11 修，见下）：短促密集的爆发走另一档，所以日志里的
`解码错误风暴` 有两种字符串，别把第二种当成新的故障。

> **2026-10-11 真机抓到反例：这条判据看不见"短而密"的爆发 —— 已修。**
>
> 那局日志开场（`22:53:59.334` → `22:53:59.378`）有 **260 条**坏字节事件
> （`NULL: obu_forbidden_bit out of range` / `NULL: Failed to parse temporal unit`；
> 同一刻落两遍，日志里 520 行 —— 判据只看时刻，重复与否一并去重），
> 应用侧**一行响应都没有**。回放 `recordDecodeErrorHit` 的量：
>
> ```
> 坏字节行: 518        （该窗口内匹配的行数；比 520 少 2 行在窗口边上，不影响结论）
> 时间跨度: 22:53:59.334 → 22:53:59.378   (44 ms)
> 去重后窗口内最多只攒到: 9 条   (门槛 12)
> ```
>
> 不是巧合，是算术：一条命中要求距上一条 **> `PlayerTuning.decodeLineDedupe`（5ms）**，等于把
> 命中率钉死在 200/s。要凑够 12 条，风暴跨度**至少 11×5 = 55 毫秒** ——
> 于是**任何短于 ~55 毫秒的坏字节爆发，无论刷多少行，都到不了门槛**。
>
> 上面那条"数包不数行"的意图没问题，漏掉的是它另一面。而且这一族和条目 18 那族
> 恰好互为镜像：**会话族是签名没覆盖（78 行认不出），这一族是认得出却数不够
> （260 条数成 9）**。旧判据是照着"几秒钟几十条"那种**稀疏而长**的风暴调的
> （`controller.dart` 的注释记的就是"实测那一局 6 秒里就有几十条"），
> 而这一局是**密集而短** —— 另一种形状，判据从来没见过。
>
> **修法（`PlayerTuning.decodeErrorDenseBurst`）：不动那条已调好的稳态判据，另加一档
> "100 毫秒内 20 行、不去重"。** 两档任一满足即上报，走同一个动作。
> 「同一个包被三层各记一行」和「两个不同的包相隔 3ms」在时间上分不开，所以这一档
> 干脆不靠时间去重，改靠**体积**把三层重复挡在外面：单个包最多记 3 行，
> 凑不出 20 —— 要 20 行等于 7~10 个坏包挤在 100ms 里。实测那场 260 条，13 倍余量。
>
> 为什么**只加给坏字节这一族**：先查了 5484 那次我们自己的 `video-reload` 产出
> （`controller.dart` 里记着"92 行"），那 92 行是
> `hevc: Could not find ref with POC …` + `Failed to decode frame (invalid session, -12903)`
> —— **一条都不匹配坏字节签名表**（`invalid session` 匹配的是**会话**那一族），
> 所以这一档不可能被它误触发。反过来，会话那一族**不能**加密集档：那 92 行里就有
> `invalid session`，加进去会把"镜像给的字节"和"本机解码器"两个相反的结论搅在一起。
>
> 拿真日志回放两档（按 Dart 的语义逐行重放，`docs/logs/` 里那三份）：
>
> ```
> 日志 4 / 6（同一局）  匹配 524 行，全在 22:53:59.334 → .378（44 ms）
>   稀疏档窗口内峰值 9 条（门槛 12）→ 首次上报：**整场没有**   ← 病还在
>   密集档首次上报：22:53:59.344                                ← 爆发头 10 毫秒
> 日志 3                匹配 0 行 → 两档都没出
> 日志 6 其余 65 分钟    匹配 0 行 → 密集档全场只出这一次
> ```
>
> 单测在 `decode_error_test.dart` 的「密集档」一组：那条 44ms/260 条逐字回放
> 同时钉住"稀疏档整场看不见"和"密集档第 20 行就报"，反例是三层重复（3 条）、
> 换集边界的零星 1~2 条、以及正好铺满 6 秒的 12 条。

### 19 — 暂停态下回前台：重建解码器不许把播放自己拉起来（MEDIUM，2026-10-12 新增）

前置：与条目 18 同一档 —— 任意一集在播、**AV1 硬解**（心跳行
`CDN 看门狗: 余量 … hwdec videotoolbox …` 能看到它）。差别只在**播放状态**：
**手动按暂停**，画面停在最后一帧、控制条是暂停态；确认心跳行里 `播放中 false`
（那句取自 `_startStallTicker()` 的 `播放中 ${playerStatus.isPlaying}`，
`PlayerTuning.heartbeatSeconds = 10`（见 `player_tuning.dart`），所以 10 秒内必有一拍能对上）。

步骤：**保持暂停**退到后台 **≥5 分钟**（锁屏或切走都行），然后回到 app。

病根与 18 是同一件事：iOS 挂起 app 时作废 `VTDecompressionSession`。18 那条判据修好的
动作本身曾经留过个缺口 —— 它重开 Media 时**不带播放意图**，用户按的暂停会被丢掉：

- **那个缺口 2026-10-12 已经修了**（`7eb5a64a2`，已在 main）。修之前 `refreshPlayer()`
  返回的是 `return ctr.open(media, play: true);` —— `play:` **写死 `true`**，函数签名
  `Future<void>? refreshPlayer()` 里也没有"要不要接着播"的入参。现在签名是
  `Future<void>? refreshPlayer({bool? play})`（见 `refreshPlayer()`），返回的是
  `return ctr.open(media, play: play ?? playerStatus.isPlaying);` —— 不传参时按
  "当前是不是在播"决定，暂停态得以保留。（对照 `_createVideoController()` 里另一条重开路径，用的是
  `play: false`。）
- 触发它的 `_sampleDecoderSessionFailure()` 闸门在函数开头那段，只挡
  `isSeeking` / `_processing` / `onlyPlayAudio` / `isBuffering` /
  `bufferedAhead <= 0` / `!_hasVideoTrack` —— **不读 `playerStatus`**，暂停态照样进得来。
  这是**有意**的：会话作废该修就修，只是修完得把播放意图还原回去。命中 6 条 / 3 秒
  （`PlayerTuning.sessionFailBurst`、`PlayerTuning.sessionFailWindow`，见 `player_tuning.dart`）后打日志、
  调 `refreshPlayer()`（返回值忽略）。
- 缺口没修时为什么会丢：重开之后 mpv 一上报 playing，播放器就把 `playerStatus` 置成
  `.playing`，而用户按的暂停**没有任何地方记着**（全仓没有 `userPause` 之类的标记）。

对比 **条目 13**：那条是**换源路**，同一口径 —— `_switchTo()` 里
`final wasPlaying = plPlayerController.playerStatus.isPlaying;` →
`await playerInit(autoplay: wasPlaying);`。两条路现在是一致的。

⚠️ **本条现在验的是"修好了没有"，不是"缺口长什么样"** —— 代码已修，但**真机还没验过**
（欠账记在 S1/N4），所以下面两边仍要照跑。

通过：
1. 那条重建行**照出**（说明暂停态没有被判据挡住，会话作废照样认得）：
   `CDN 看门狗: 硬解会话失效（3s 内 6 条），本机解码器被系统作废 —— 重建解码器`
   （逐字，`_sampleDecoderSessionFailure()`；判定它的原始 mpv 行是
   `av1: Failed to decode frame (invalid session, -12903)` 与
   `av1: vt decoder cb: output image buffer is null: -12909, reconfig 1`，
   签名表见 `lib/utils/decode_error.dart:98` 的 `kDecoderSessionFailureSignatures`，
   `:101` `'invalid session'`、`:104` `'output image buffer is null'`）。
2. 重建之后**播放仍是暂停** —— 心跳行里 `播放中 false` 不变、`位置 Ns` 停在暂停那一刻
   不往前走；画面回到暂停的那一帧，不自己动。

失败（**说明 `play ?? playerStatus.isPlaying` 没兜住**）：回前台后画面**自己动起来**，
心跳行从 `播放中 false` 翻成 `播放中 true` —— 那就要查 `refreshPlayer()` 的调用点上
`playerStatus` 当时到底是什么（见 `refreshPlayer()`）。
注意 30s 冷却（`PlayerTuning.sessionFailCooldown`，见 `player_tuning.dart`）只压"动手"的频率，
不影响这一次的播放意图。

⚠️ 真机上要看清的**第一件事**是"签名到底响没响"：暂停时 mpv 不一定在解码，那两条会话
行有可能一条都不出。若如此，本条在真机上会表现为"什么都没发生"，缺口只是**潜伏**
（用户恢复播放时 mpv 重新解码，签名才会响，而那时用户本来就要播）—— 那就不是本条失败，
而是"要换个前置才复现得出来"。先记下这一次的观察再下结论。

### 20 — 备注：换源轮次里 `now` 的取样时刻偏早几秒（无需真机验证）

一轮换源的 `now` 是在**轮次开头**取的（`_pickFastestCdn()` 里
`final now = DateTime.now();`），而它要到探完对象大小（同函数里
`await CdnSpeedTest.probeSize`，预算 `probeMicros`/`probeConnect`/`probeReceive` 各 3s，
`lib/utils/cdn_speed_test.dart:18-20`）和并发测速（`_pickFastestCdn()` 里那几处 await，`autoMicros`
6s / 快档 `quickMicros` 3s，`cdn_speed_test.dart:30`/`:40`）**之后**才被拿去记账 ——
也就是相对"读数真正落地的时刻"偏早约几秒（最多探大小 3s + 测速 6s）。受影响的是它喂的
那几处时间窗：`_cdnRecentlyTried` 的 3 分钟 / 30 分钟（`_pickFastestCdn()`，窗口 `CdnTuning.retryAfter`
/ `CdnTuning.deadRetryAfter`，见 `cdn_tuning.dart`）、`_cdnState.triedAt[service] = now` 的 3 分钟冷却
（`_pickFastestCdn()`）、`_cdnChampion` 的 6 小时过期（`_pickFastestCdn()` 里对它的调用，窗口 `CdnTuning.recordExpiry`，见 `cdn_tuning.dart`）、
`_recordCdnSample` 的 30 分钟覆盖与 6 小时过期（`_pickFastestCdn()` 里那次调用，`CdnTuning.recordReset` 见 `cdn_tuning.dart`）。
**对着这几档窗口，偏早几秒不产生行为差异**（窗口比误差大两三个数量级），所以它是备注、
不是 bug。**无需真机验证。**

（注意它**不在**解码恢复那条路上：`_awaitRecovery` 的参照点是等它开始时取的 `start`、
判据用的是 `elapsed`，那里没有"偏早几秒"的取样。）

### C. 播什么、什么顺序（这一局靠撞）

**目标症状**（就是那条唯一能通向 P3 的坏法）：把**视频轨那一条 URL** 喂坏 —— 屏幕上是
**「声音还在、画面冻住/黑」**，而缓冲/余量读数可能还很健康。**别去钉 cosov 等 P3**。

> **为什么别钉 cosov**（2026-10-12 两局实测结论）：cosov 现在坏的是**第一种坏法**
> —— 测速一读就断流（`Connection closed while receiving data` → `无样本`）→
> **预检档起播后很快就救走**（`CDN 自动切换: 基线无有效速度，直接切换`；
> log 8：`14:43:53.540` 预检 → `14:43:59.400` 已切到 hw，**~6 秒**；README 记的起播到恢复 14 秒）。
> 那比 P3 快：P3 要看门狗**攒满一个时间窗**才认死锁（1s 一拍、每拍都看；强指纹成立时
> `PlayerTuning.noVideoWindow` 3s ≈4 拍，否则 `PlayerTuning.noVideoWindowWeak` 8s），定罪后**直接**就地重建。
> 钉着它，永远轮不到重建。

**判据 = 时间窗（2026-10-15 起，取代「数探」）**：ticker **1s 一拍、每拍都看**；七道门
（`onlyPlayAudio` / `isLive` / `position <= 0` / `isSeeking` / `_processing` /
`_rebuildingRenderContext` / `isBuffering`）全不成立、且画面为空（`_hasVideoTrack` 假）这段
状态**连续攒满一个窗**才定罪（`_checkNoVideoTrack`）。**窗口档位由强指纹选**：强指纹成立走
`PlayerTuning.noVideoWindow` = **3s（≈4 拍：开窗 1 拍 + 3 拍）**，不成立走 `PlayerTuning.noVideoWindowWeak` = **8s**。
**强指纹是档位开关，不是只贴个后缀**：它成立才走 3s 档，且上报行末尾带 ` [强指纹]`（**后缀 =
「这次走的是 3s 档」的标记，两者等价**）。「强指纹」= `video-codec` 非空 **且** `hwdec-current`
非空 **且** 位置比上一拍大；值钱的是 `hwdec-current`：**由空串变非空只有「解码器真的开了」
这一种可能**（2026-10-15 同局核过 `02:40:16 hwdec 0x0` → `02:40:27 hwdec videotoolbox`）。
⚠️ 位置冻住（`position` 不比上一拍大）会让强指纹不成立 ⇒ 自动走 8s 档、上报行**不带**后缀 ——
**8s 档是留给「视频轨饿死」那种误报风险的，它的正解是换源、不是重建**。**定罪后直接**调
`_rebuildRenderContextOnNoVideo()`（「钉住输出尺寸」那一档已整个删掉）。**上报行后缀**（**基串
一字不改**）顺序固定：` [本媒体已重建 N 次]`（仅当 N>0）在前，` [强指纹]`（走 3s 档的标记）在后；
旧的 ` [本次媒体已自愈过]` 已删。

**怎么摆**：

1. 随便挑一个 **≥10 分钟**的长视频（和 log 11/13/14 那几条同类即可），**从头开播**。
2. **先让它正常播一段**（至少 20~30 秒，位置越过起播）再谈坏 —— 无视频轨判据有硬前置：
   `position.value <= 0` 是该函数里的一道门，位置还在 0 时该拍直接返回、不计入窗口
   （`_checkNoVideoTrack`），所以**「从头开播立刻坏」这种局面永远攒不满窗、探不到 P3**。
   这就是"必须播到中途才让它坏"的原因。
3. **耐心等**。这一局**靠撞**，没有可靠的触发按钮：
   - log 14 那局第一次 `无视频轨` 出现在**起播后 58 秒**（`20:27:37.940` 起播 →
     `20:28:35.986` 第一条无视频轨），随后 `20:29:57` / `20:31:49` 又各来一次 ——
     但它那局是**链路整天在坏**（全篇 12 条含 `无视频轨` 的行、每条前面都跟着
     `tls: Error in the pull function` / `IO error: Operation timed out`）。
   - log 11 那次是**续播到 `898s`** 时画面冻住（`17:30:37.378`）—— 也是"播着播着才坏"。
   - **正常网络的日子里整局可能一次都不出现**。

**想提高命中率**，只有下面这几招，都有依据：

- **多播几条视频**：每条新视频 = 一次**新的 URL 抽样**。log 14 那三次重建就分别落在
  **三条不同的视频**上（`42039840115` / `37644140816` / `25930240173`）。看完一条没撞上，换下一条接着播。

  + 新的 `选流:` 行），等于对同一集再抽一次新 URL。log 14 里就有中途切到 `画质 116` 的
  `选流:` 行（`20:28:12` / `20:29:46` / `20:31:40`）。
- **别把「挑冷门 CDN」当招用**：这一条**没有存档依据** —— 坏的是**某一条 URL 那一刻的字节**，
  跟"哪个 CDN 冷门"没有观察到的关系。唯一有实据的 CDN 结论就是上面那条"别钉 cosov"。

  - **健康播放整局 0 条，这是设计而非运气**：定罪要同时满足「输出没配上 + 有视频轨在解码
    + 没暂停 + `n`/`rendered` 连着两拍（≈5s）不涨」四个条件；健康播放 `rendered` 约 9 次/秒，
    第二拍之前早就翻篇了。**所以"整局一条 `VideoOutput.Probe` 都没有"就是健康的样子**，
    别当成探针没插上。
  - **要回答的三个问题**：
    1. **死锁局里 `start` / `ongoing` 那几条的 `n` 是 0 还是 >0**。`n == 0` 就是「回调
       **压根没跑**」的铁证（⇒ 原生侧可以自己补一帧撬开）；`n > 0` 却仍 `configured:false`
       ⇒ 回调跑过但画不出来，得从别处下手。**这两种情况修法相反**，这就是探针存在的唯一理由。
       ⚠️ **但先看 `mainLagMs`**：iOS 侧 mpv 的 update callback 是先 `DispatchQueue.main.async`
       再进 `VideoOutput.updateCallback()` 的（`TextureHW.swift`），所以 `n` 数的是**那一跳 main**，
       main 一卡 `n` 就冻结 —— 那种时候的 `n == 0` 是**假结论**。`mainLagMs` 明显偏大就说明是
       main 卡住，不是 mpv 没回调。
    2. **有没有 `read-blocked`**：读 mpv 属性要拿核锁，核锁被长持时探针自己也读不动 ——
       那与「回调没跑」是两回事，单独一行说清楚（超时阈值 1.0s，正常读是微秒级）。
       `read-recovered` 带回 `blockedMs`，告诉那次卡了多久。
    3. **`size`** —— 黑屏时它应是 `[0.0,0.0]`（还没渲染过）或 1×1 / 上次兜底值。
  - **一次黑屏的形态**：`start`（连两拍没动静，≈5s）→ `ongoing` 每 5s 一条、**封顶 6 条
    （≈30s）**，之后静默到 `recover` —— 中后段不缺氧，app 侧 `无视频轨` 本身每 ~2.9s 一行。
    定罪后采样从 2.5s/拍切到 **0.5s/拍**（`quietSamples` 涨得快就是切了），黑屏前 30 秒的
    形态看得更清。`recover` 带 `quietMs`＝这次安静了多久。

1. **`CdnSpeedTest.sampleLeadMs` = 5000ms**（计划里叫 `_kCdnSampleLead`，已搬到
   `lib/utils/cdn_speed_test.dart` 的 `sampleLeadMs`，由 `_starveOffset` 传入）——
   取样点越过缓存末端的量。
   - 太小：样本落回热的缓冲区间（实测同一偏移热 19.2MB/s、冷 0.683MB/s）→ 基线虚高、
     除掉它之后比值塌下去、永不切换（`目标偏移` 又贴回缓存末端/播放头字节）。饥饿时最致命，
     因为那时 `cacheEnd == playhead`，这个 lead 是唯一的余量。
   - 太大：取的字节超出播放头接下来要用的范围，量到的速度不代表即将播放的那段；
     对短对象还会被 `size − readWindowBytes` 夹到同一个偏移，所有镜像打平。

2. **`CdnTuning.decodeCleanWindow` = 4s**（`cdn_switch_mixin.dart`）—— 判定解码档恢复所需的安静时长。
   - 太小：慢一点才坏的镜像在下一场风暴来临前就被判
     `解码错误档换源后 Ns 无新报错，判定已恢复`，几秒后画面又冻（来回弹）。
   - 太大：真的好镜像被判未恢复 → 多余的重载/位置抖动；而每次失败都禁一个 host，
     候选被耗光，正常的网络最后落到放弃。

3. **`CdnTuning.decodeRecoverGrace` = 4s**（`cdn_switch_mixin.dart`）—— 旧流的报错不算新镜像账的宽限期。
   - 太小：重载（实测 5~10s）期间旧流还在排空，那些报错刷新 `lastDecoderCorruptionAt`，
     干净窗口永远满足不了，连好候选也判未恢复 → 干净地放弃。
   - 太大：新镜像真实的坏字节被忽略那么久 → 坏镜像看着"干净"，在画面还冻着时被判已恢复
     （正是条目 7 修掉的那个 bug）。
   - **注意它必须按时刻滤**（`lastDecoderCorruptionAt` 早于 `start + grace` 的整段忽略），
     不能只用来重置一个 `since`：grace 和 `CdnTuning.decodeCleanWindow` 等长时，后者会把
     宽限期想区分的那件事原样抹平（判据退化成"离最近一次报错满 4 秒"，而那次报错可能
     来自旧流）。这两条谁改都必须一起改。

4. **`CdnTuning.decodeRecoverWindow` = 18s**（`cdn_switch_mixin.dart`）—— 解码档等待恢复的总上限。
   - 太小：重载（5~10s）+ 宽限（4s）+ 干净窗口（4s）≈ 13~18s 塞不下，正好在镜像快要自证干净时
     判失败 → 提前禁 host、来回弹。
   - 太大：一心想换掉一条真坏的镜像时，每次尝试都要烧这么久；配上 `CdnTuning.maxAttempts = 3`，
     一轮可以在冻着画面上耗掉约 54s 才放弃。

     的 w/dw）翻真 —— 画面照样是黑的，判据却不再定罪 ⇒ **就地重建这条唯一的救援路也不触发**
     ⇒ 永久黑屏，只能杀进程。现在这个病是 11s **能自愈**的，换成救不回来的不划算。
   - ⚠️ **会搅浑取证**：这一版同车上 fork 的常驻 `VideoOutput.Probe`（要回答"死锁时
     `_updateCallback()` 到底有没有被叫过"，见上文那条）。若 `force-window` 真把竞态压住了，
     这一局就**不复现死锁** ⇒ 探针按设计整局 0 行，**"压住了"和"探针没插上"在日志里长得一样**，
     探针存在的唯一理由也随之落空。
   - **顺序**：先拿探针的证据，再单独出包试它。真试的时候，判读方法是：开 mpv verbose 取日志，
     看那对 `VO: [libmpv] …` → 约 200ms 后 `libmpv_render: Window size: …` 是否**装载时
     就出现**（健康装载必有一对，坏的那次两条都没有）；再**连跑 ~20 次装载**看是否一次都不缺。
     **同时必须盯 `_hasVideoTrack` 会不会翻真** —— "翻真了但画面还是黑的"就是踩中了致盲那一条。

## 复查追加的四处（2026-10-11，对抗性复查 diff 之后修的）

这四处都不是新功能，是上面条目的补洞 —— 前一轮的修复各自留了一条"作废的轮次仍会提交状态"
的缝。查的时候跟对应条目一起看：

- **条目 2 的补洞（HIGH）**：一轮测速中间有两次数秒级的 await（探大小、并发测速），期间
  换画质/换集会把这轮作废，但作废的那一轮**仍在往下写** —— 最毒的是把**旧对象**的字节总长
  写回 `_cdnState.objectSize`。它是一次性的（只有 `size == null` 才探），被填回去就整集不再探第二次，
  此后每轮都拿旧长度算偏移，落到短一截的新对象上必得 416 → `unmeasurable` → 自动换源整集失效。
  查法：换画质那一下之后，`目标偏移 …/<size>` 里的 `size` 必须是**新画质**的长度；若一直沿用
  旧值（或此后每轮都 `越界(416)，放弃本轮`），就是这个洞。现在两处 await 之后都有
  `_roundVoided(generation)` 复查，作废即 `return null`，一个格子都不落。
- **条目 8 的补洞（MEDIUM）**：`_cdnIsAttached` 原先只挡了探测定时器，挡不住**在途的那一轮**：
  旧页的 `_autoSwitchLoop` 已经在跑，回调被新页覆盖也拦不住它，它会拿**旧视频**的 URL 去
  reload 新视频的播放器。查法：跳相关视频后看有没有"第N次 -> …"来自旧视频；现在整个循环里
  三处闸门都带 `!_cdnIsAttached`。
- **条目 7 的补洞（MEDIUM）**：`_awaitRecovery(decode:true)` 返回 false 有两种含义 ——
  "新镜像还在吐坏字节"和"这一轮作废了/页面关了"，而原来的禁 host 把两种都当成前者，
  凭空封掉一条从没被播出过的镜像 30 分钟。现在禁 host 前要求这一轮仍然有效。
- **条目 6 的补洞（MEDIUM）**：挂载新页（相关视频跳转，旧页不 `onClose`）从来不重置共享
  播放器的解码账，于是旧视频的残余计数让新视频几条零星报错就凑满风暴门槛，没过期的静默期
  又把新视频真正的风暴按下去。现在 `attachCdnSwitch()` 里调 `resetDecodeErrorAccounting()`。

## 复查追加的第二批（/code-review，2026-10-11）

这六个是自动代码复查抓出来的，其中两个就在第一批的修复里（第一批修的是"作废的轮次
仍会提交状态"，这批修的是"作废的轮次在别处留下的另一边"和"恢复判定自己的时间轴"）：

- **恢复判定提前到 4s（HIGH，在第一批的修复里）**：滤掉旧流报错之后，安静时长是从
  `start` 算的（不是从宽限期结束算），于是 `elapsed >= 4 && since >= 4` 在 elapsed 刚
  够 4 那一刻同时成立 —— **一秒安静都没观察到**就宣布恢复，宽限期又从另一头变成空转，
  跟 `CdnTuning.decodeRecoverWindow` 注释里的"宽限 + 干净窗口（≈8s）"自相矛盾。现在从宽限期
  结束算，合计 ≈8s。查法：看 `解码错误档换源后 Ns 无新报错` 里的 Ns，成功时它必须 ≥4。
- **跳相关视频回来之后永久静默（MEDIUM）**：旧页被顶掉时停掉自己的探测定时器，而返回时
  没有任何东西重挂 —— 连换集都不恢复（`restartCdnProbe` 只重启定时器，不重挂回调）。
  修法：`attachCdnSwitch()` 改成幂等的，并在 view 的 `didPopNext`（返回本页）里调它。
  查法：A → 相关视频 B → 返回 A → 制造一次卡顿，`CDN 自动切换:` 必须照常出现。
- **旧页退出清掉现役页的解码账（MEDIUM）**：`detachCdnSwitch → resetCdnAutoSwitch` 会动
  共享播放器的账，而被顶掉的旧页退出时那份账是现役页的。修法：只有"退出时仍是现役页"
  才清，判断在回调置空前取（置空之后 `_cdnIsAttached` 自己就成假了）。
- **时钟回拨会让解码判据整个 session 失效（LOW）**：`recordDecodeErrorHit` 的去重比较
  在回拨后成负数 → 此后每条报错都被当成同一包的副本吞掉，而淘汰条件对未来时刻也不成立
  → 记录清不掉。和条目 16（`recordTooOld`）是同一件事，按同样口径修：负差值算新的，
  落在未来的旧记录清掉。单测 `test/utils/decode_error_test.dart` 里钉住了。
- **`_cdnState.triedAt` 记在作废判断之前（LOW）**：候选冷却在测速**之前**写入，于是作废的那一
  轮仍会给新对象留下 3 分钟冷却（`_cdnState.triedAt` 是刻意为换画质保留的）。已挪到两道作废
  判断之后。影响本来被三遍候选循环的第三遍（忽略冷却）挡掉大半，所以只是让注释里那句
  "一个字节都不许提交"变成真话。
- **`disableAudioCDN` 在换源时被忽略（MEDIUM，**既有**，不是这次改出来的）**：音频那条
  重写没把 `isAudio: true` 传进 `getCdnUrl`，于是"音频不跟随 CDN"这个设置只在起播时
  生效、一换源就失效 —— 正是这个开关要避免的"部分视频无声"。`cdnUrlFor` 现在带
  `isAudio`。**修复前就是这样**：那时换 URL 的函数叫 `CdnSpeedTest.urlFor`，签名里
  根本没有 `isAudio` 这个参数（`urlFor(urls, service)`）—— 这一轮才把它挪成
  `VideoUtils.cdnUrlFor` 并补上 `isAudio`。顺手修了。
  查法：打开该设置，换源后看音频 URL 的 host 有没有跟着变。

## 复查追加的第三批（2026-10-12，跨页守卫那一轮之后）

承 `917171998` 那次修复（尾段补 `_cdnIsAttached`）。复查时把整个 mixin 里**所有会碰播放器**
的地方穷举了一遍，得三条：**第一条在混入层无解，只能记着**；**后两条本轮已修**
（其中第二条只有真机日志当证据，见下）。

- **换源重载本身拦不住（MEDIUM，既有；本轮确认在混入层无解）**：尾段那句 `_roundLive`
  只能掐掉重载**之后**的动作（补 seek、恢复判定、假"成功"），**掐不掉重载**。
  因为页面侧的 `playerInit`（`lib/pages/video/controller.dart:747`）干的事就是
  `await plPlayerController.setDataSource(NetworkSource(videoSource: videoUrl!, ...))`
  （`:766`），而 `videoUrl` 是 `_switchTo()` 在调用**前**几行写进去的
  —— 也就是**重载发生在 `playerInit` 内部**。`setDataSource()`
  里没有任何"你是不是现役页"的检查。
  要紧的是：从 `_autoSwitchLoop()` 里那道闸门一路走到 `_switchTo()` 里那句 `await playerInit`，
  **中间一个 `await` 都没有** —— 新地址 `videoUrl = newVideo;`（`_switchTo()`）也是在这段同步
  代码里写下去的。所以旧页决定重载的那一刻**它确实还是现役页** —— 用户还没来得及跳走。
  这不算"漏了一处"，是**站在那个点上无从拦起**。
  后果：重载在飞的时候跳相关视频，它仍可能落地（`setDataSource` 里 `await pause()` 之后的
  `_createVideoController` 一样可能在 `playerInit` 返回前跑完），把播放器换成**旧视频**的地址，
  并按 `setDataSource()` 重置共享的 `position`/`buffered`。
  与 `_autoSwitchLoop()` 里 `refreshPlayer()` 兜底那条**不是一回事**：兜底 `refreshPlayer()` 经两个独立分析确认够不着
  （`!switched` 成立 ⟹ 循环每次都从 `_autoSwitchLoop()` 里那几处 `break` 出去，
  而那几处都在同函数那道闸门之后的**同一段同步代码**里 —— 中间没有 `await`，所以执行到
  兜底那句时本页必然还是现役页；给它加 `_roundLive` 是死代码）。本条则相反：够得着，
  但无从拦。**要修得给 `PlPlayerController` 加"发起者身份"**（非现役页发起的换源直接丢弃），
  动的是播放器核心，单独一轮做。
  **真机观察项**：跳相关视频后偶发"画面跳回上一个视频 / 缓冲被清空"即命中 —— 这条只能真机看。
- **补落点的那一发 seek 会悬在重载里，醒来时落到新页的片上（MEDIUM，本轮已修 —— 但只是收窄）**：
  `_restoreResumePosition` 补 seek 时调的是 `player.seekTo(target)`，走 `seekTo` 的默认档
  `isSeek = true`；而 `lib/plugin/pl_player/controller.dart` 的 `seek()` 里
  `seek()` 第一件事是 `await _videoPlayerController?.stream.buffer.first`。
  换源重载期间那条流要几秒才吐第一个 buffer（新文件还没 demux 出来），于是这一发 seek
  **整段悬在那里**；悬着的这几秒里用户跳相关视频，它醒来时 `_videoPlayerController` 已经
  被新页换成了**别的视频** —— seek 于是落到新页的片上，还会顺手清掉新页的弹幕
  （`seek()` 紧接着那句 `danmakuController?.clear()`）。`_roundLive` 拦不住一发**已经发出去**
  的调用：它只挡下一拍，收不回在途的。最多 8 发可以同时悬着。
  **真机证据**：`docs/logs/pili-console-3`，22:00:54.646/55.446/56.246/57.054 连打四发
  `CDN 自动切换: 落点 … 补一次 seek`（此时 mpv position 还是 0），而 mpv 直到 22:00:57.497
  才第一次 `timeline: queuing seek to 7.250000` —— 四发全部先悬着、后一起落地。
  **修法**：`await player.seekTo(target, isSeek: false)`（`_restoreResumePosition()` 一带）。
  `isSeek: false` 跳过那道等待，seek 在 `_roundLive` 复查之后**当场**发出去 —— 窗口从
  「整个重载期」压到「一条 mpv 命令往返」。仓里程序化 seek 本来就多用这一档
  （`bottom_control.dart:44`、`view.dart:979`、`pip_helper.dart:60` 等 10 处）。
  **这只是收窄，不是根治**：根治要在播放器里给"发起者身份"（与上面第一条同源），
  动核心，单独一轮做。**离线测不出来**：测试宿主的 `videoPlayerController` 是 null，
  `await null` 一个微任务就过，那几秒的悬停在假件上根本不存在 —— 所以这条**没有红灯**，
  证据只有上面那份真机日志。
  **复查更正**：我原先记的是「`duration.value == 0` 时 `seekTo` 把 seek 寄存到
  `duration.listen` 上」—— 那个分支**几乎够不着**（`setDataSource()`
  里就用 `duration ?? state.duration` 把 `duration.value`
  写成非零，之后也没有东西把它归零），真悬住的是 `stream.buffer.first`。两条都读过才改的口。
- **被顶掉那一页重新露面后的那几秒，还会接着动播放器（MEDIUM，本轮已修）**：
  相关视频跳转 push 新页，既不 `onClose` 旧页、也不换代。旧页在途的那一轮在
  `_pickFastestCdn` 里等探测请求时，内部只有 `_roundVoided` 复查（`_pickFastestCdn()` 里两处），
  **没有 `_cdnIsAttached`** —— 所以被顶掉多久它都活着。用户 pop 回来 → `didPopNext` 调
  旧页的 `attachCdnSwitch`（`lib/pages/video/view.dart:498`），它把 `onStall` 等回调**同步**
  装回去，`_cdnIsAttached` **立刻又为真**，而 `_cdnState.generation` 从头到尾没动过 ——
  `_roundLive` 于是重新为真。从这一刻到旧页自己的 `playerInit`
  （`view.dart:525`，**没有 await**）把 `setDataSource` 跑完之间（亚秒~几秒），播放器上

  **修法**：`attachCdnSwitch` 在幂等闸之后 `_cdnState.generation++;`，**并且同时**
  `_cdnState.autoBusy = false;`。后半句不是配套美容，是必须的 —— 一轮收尾那句

  `busy=true` 忽略，而 `attachCdnSwitch` 幂等、再也不会进来救它 —— 这一页的自动换源就死透了。
  **不复用** `resetCdnForNewObject()`：它还会清 `_cdnState.objectSize` / `_cdnState.badHosts` /
  `_cdnState.championMisses`，那些对这个**没换过**的视频对象仍然有效（清 `_cdnState.badHosts` 等于把
  已知坏的 host 重新放进来）。
  幂等闸正好把换代收窄到「只在真被顶掉过之后」：没被顶掉时 `_cdnIsAttached` 为真、直接早返回，
  不动代（普通关弹层/返回子页就是这条路）。
  **红灯**：`test/pages/cdn_switch_mixin_test.dart` 的

  修复后一条不发。两半都单独验过：只删 `_cdnState.autoBusy = false;`，第二条断言（重挂之后
