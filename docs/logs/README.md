# 真机日志（`pili-console.log` 的存档）

`lib/services/console_log.dart` 把 app 的日志写到文稿目录的 `pili-console.log`。
这里存的是历次真机验证取回来的副本 —— **手工**记的，`.gitignore:3` 的 `*.log`
把日志本身挡在版本控制之外，只有这份 README 是跟仓库走的。

**每次启动会截断**（`file.writeAsString('')`），所以一份日志 = 一次启动；
同一次启动里的连续多段测试会连在一起。8 MiB 上限。

取回命令（bundle id **带 AltSign 后缀**，用 `com.example.piliplus` 会报 error 3）：

```
xcrun devicectl device copy from \
  --device 00008140-000A78911163001C \
  --domain-type appDataContainer \
  --domain-identifier com.example.piliplus.895K68AF3F \
  --source Documents/pili-console.log --destination <path>
```

**这条命令要 USB 或者手机跟 Mac 在同一个 Wi-Fi 上** —— 2026-10-12 人在外面时
`devicectl list devices` 直接报 `unavailable`，`copy from` 报
`com.apple.dt.CoreDeviceError error 4016 (0xFB0)`、`CurrentlyAssertableStates = ( )`。

所以 2026-10-12 加了一条**不依赖同一网络**的路（**2026-10-12 真机已验证 ✅**）：
设置 →「其它设置」→
「iCloud 日志同步」→ 选 iCloud Drive 里的一个文件夹。之后 app 每 60 秒同步一次、
**退到后台立刻再同步一次**，Mac 上直接读：

```
ls ~/Library/Mobile\ Documents/com~apple~CloudDocs/Downloads/ForpiliLog/
```

**验收证据**（2026-10-12 20:32，别再用 `devicectl` 当对照了 —— 那次两条路都拿到了）：
iCloud 那份与 `devicectl copy from` 拉下来的 1500 行**逐字节相同，只少最后一行**
（`20:32:04.987 Set property: pause=true`）—— 少的那一行是快照那一刻之后才写进
本地日志的，正好证明它确实是"活着的时候拍的一张快照"，不是拷了个完整文件。
⚠️ **成功时一行日志都不打**：日志里看不到任何 iCloud 字样 ≠ 没生效，
判据是设置页副标题的「上次同步 HH:mm:ss」和 Mac 上那个文件。
⚠️ 上一版踩的坑：`bookmarkData` 必须**在 `startAccessingSecurityScopedResource()`
之后**调，反过来会抛 `The file couldn't be opened because it doesn't exist.`
（`ICloudLogPlugin.swift:136-170`）。

每次启动把上一份改名成 `pili-console-<MMdd-HHmmss>.log`，只留最近 10 份。
⚠️ Mac 上晚几分钟看到不代表没写（上传是系统的 `bird` 在跑，低电量模式会拖后），
**以设置页显示的「上次同步时刻」为准**。⚠️ 文件夹要选 iCloud Drive 里的，
选成「我的 iPhone」就同步不到 Mac。

## 引用这些证据时注意

- **`CDN 看门狗: 余量 …` 心跳是播放器单例打的**，不属于任何一页 —— 不能拿它当
  "某页还在活动"的证据（`pl_player/controller.dart` 的 `_startStallTicker`）。
- **签名匹配大小写无关，但你 grep 日志时要自己注意大小写**：日志里是
  `av1: HW accel end frame fail.`（大写 `HW`），小写模式一条都匹配不到 ——
  2026-10-11 复核时就被这个坑过一次，把 78 行数成了 52 行。
- **同一个日志里有两个"位置"，打开失败后会互相矛盾**（日志 6 的
  `23:24:08` → `23:26:10` 一段）：
  - 看门狗那行的 `位置 215s` 是 `position.value`，它**只由 `stream.position`
    事件更新**（见 `_startListeners()`）；mpv 没有媒体就不发事件，于是它**冻在
    最后一个好值**上。
  - `CDN 自动切换: … @0s` 和 `目标偏移 … (位置 0ms/…)` 用的是传进来的
    `videoPlayerController?.state.position`，它是 media_kit 的当前状态，**换媒体
    后归零**。
  - `refreshPlayer()` 拿的正是后者当起点：`media.copyWith(start:
    ctr.state.position)` —— 所以一次 `Failed to open` 之后，重建会把播放位置
    **打回片头**（实测 `23:24:16 start=215.000` → `23:24:28 start=0.000`）。
  以后见到"看门狗说 215、mixin 说 0"就先怀疑打开失败，别当成两条判据打架。
  - **别急着说"换源会丢位置"**：换源那条路有落点修正兜着 ——
    `CDN 自动切换: 落点 0ms 落后于 391633ms，补一次 seek`（`23:51:09` / `23:51:41`）。
    它比的是**另存的目标**，所以新流自己落在 0 也能纠回来。
    它修不了的是"**目标**读到 0"（就是上面那种）。所以判断有没有丢位置，看那一轮
    有没有 `落点` 行：`23:26:10` 那次切到 cosov **一行 `落点` 都没有**，
    说明目标本身就是 0，落点也是 0，没得纠 —— 位置真的丢了。
- **"余量"是推出来的，位置读数一坏它就假高**：看门狗那行的 `余量 = cache-time − 位置`。
  位置一归零（就是上面那种打开失败/重载），余量立刻变成 `645s` 这种**看着极健康**的假值
  —— log 10 的 `17:19:42` 就是 `余量 645s 位置 0s (cache-time 645s)`。这时判据 3 的
  **第一支（`bufferedAhead < 阈值`）直接失明**，接住它的是**第二支（遥测失真：
  `余量 > 缓存上限 96s` 的 3x）**；log 10 里那几条 `CDN 遥测失真:` 全是第二支打的，
  一条 `CDN 缓冲饥饿:`（第一支）都没有。所以**别拿"余量很大"当链路健康的证据**，
  先看同一行的 `位置` 是不是 0。顺带：第一支失明也让 `仍在饥饿，再次上报` 那一支
  永远等不到它的形态 —— 另一半见 `_starveLastReportAt` 的"恢复即清空"。
  **（2026-10-12 更新）第二支从这条口子里分出去了**：失真不再挤在 `starve` 里，改走
  播放器侧新出口 `onTelemetryDiverged` → 页面侧 `_CdnTrigger.diverged`（标签
  「画面已冻」）。它**单独吃「放弃冷却 / 进展门槛」两道闸的豁免**（这两道原先只给
  解码错误开），但**不吃**「不看速度」那一条。两处判据因此不该再混着数：
